# ADR 0002 — Always elevated

- **Status:** Accepted
- **Date:** 2026-08-04 (in place since v1.9.0 or earlier: v1.0.0 already shipped "automatic UAC elevation")
- **Depends on:** ADR 0001
- **Referenced by:** ADR 0004 (what an elevated process must not run), ADR 0013 (no second UAC prompt for the setup), ADR 0014 (machine scope only), ADR 0015 (`ElevationRequirement: elevatesSelf`), ADR 0018 (retry without elevation, issue #12)

## Context

Installing and removing software needs administrator rights. The app drives winget through
queues of installs, upgrades and uninstalls, and runs without a console (`-noConsole`), so there
is nowhere for winget to stop and ask.

## Decision

WinGet Studio **always runs elevated**, asking once, at startup.

- The exe carries a `requireAdministrator` manifest, generated by ps2exe from `-requireAdmin` in
  `build.ps1`, so Windows shows the UAC prompt before the process starts.
- `src\main.ps1` checks `IsInRole(Administrator)` as its first act and, if not elevated,
  relaunches itself with `Start-Process -Verb RunAs` and exits: `powershell.exe -File <script>`
  when run from source, the exe itself otherwise. A cancelled UAC prompt exits silently. This is
  the fallback to the manifest, and the reason `main.ps1` is a separate file (ADR 0001).

## Consequences

**Positive**
- One UAC prompt per session, however many machine-scope packages a queue holds (the cost
  issue #12 sets against per-operation elevation).
- The self-update of an installed copy runs the setup with no second prompt (ADR 0013).

**To watch**
- **Per-user packages can land in another profile.** If the elevated account is not the
  signed-in user, a per-user package installs into the administrator's profile without saying
  so. `Test-ElevatedUserMismatch` (`Tab.Install.ps1`) compares the console user from
  `Win32_ComputerSystem` with the current identity; when they differ and the chosen scope is not
  `Machine`, the log warns once per session and suggests `Scope: Machine`. If the check cannot
  tell, it stays silent rather than raise a false alarm.
- **winget refuses to uninstall or repair user-scope packages from an elevated process**
  ([issue #12](https://github.com/FedeB2160/WinGetStudio/issues/12)). For packages of type `exe`,
  `burn`, `inno`, `nullsoft` and `portable` installed per user — winget's own portables included —
  it fails with `0x8A15007D` (`-1978335107`, `APPINSTALLER_CLI_ERROR_ADMIN_CONTEXT_ACTION_PROHIBITED`):
  *"The package installed for user scope cannot be uninstalled when running with administrator
  privileges."* This is a deliberate security block in winget (`UninstallFlow.cpp`:
  `AdminExecutionShouldBlockUserScopePackages` plus `Runtime::IsRunningWithNonDefaultFullToken()`;
  the same check exists for `repair` in `ShellExecuteInstallerHandler.cpp`) and no option gets
  round it. MSI, MSIX and Store packages, and install and upgrade, are unaffected.
- Issue #12 listed three ways out: retry unelevated through a scheduled task only when needed; an
  unelevated app with elevation per operation, the model of the winget CLI and UniGetUI; an
  unelevated app with an elevated helper process per queue. **ADR 0018 chose the first**, with one
  correction. This ADR said to repeat the command as the signed-in user, so that it would run as
  the package's owner even when elevation used another admin account. But elevated, the per-user
  packages in the list belong to the *elevated* account, so the retry runs as that same account
  without elevation, and when the elevated account is not the signed-in user it does not retry at
  all.
- Everything that runs inside this process runs as administrator, which is why text that reaches
  a command line is guarded (ADR 0004) and why the installed form is machine scope only (ADR 0014).

## Alternatives considered

The sources record no alternative weighed when elevation was first adopted. For issue #12, the
three approaches above are weighed in ADR 0018, which chose the first.
